# 目的

「660万件」と「12万人」を比較して件数が多い方を一律に深刻とするだけでは、事故後の本人リスクを正しく捉えられない。パスワードは変更できるが、顔写真や生年月日、本人確認書類、過去の雇用情報は変更できないか、変更が困難である。逆に、一件でも管理者用秘密鍵やAPI資格情報が流出すれば、多数の下流データへ波及し得る。

本資料は、Denno Watchの個別事例を**データ量ではなく、被害の性質と残存期間**でも比較するための分類体系を定義する。

# 件数以外の八つの評価軸

| 軸 | 質問 | 高リスクになる条件の例 |
| --- | --- | --- |
| 感度 | その情報単体で本人・組織へ大きな不利益を与えるか | 医療、金融、認証、本人確認、マイナンバー |
| 変更可能性 | 流出後に無効化・変更できるか | 顔写真、生年月日、過去の雇用履歴は変更困難 |
| 悪用可能期間 | 何年後まで価値が残るか | 本人確認書類画像、静的識別情報 |
| 連結可能性 | 他の流出情報と結合して価値が増すか | 氏名＋住所＋電話＋購買履歴＋本人確認画像 |
| 到達性 | 攻撃者が取得・閲覧したことをどこまで確認できるか | 外部転送ログあり、取得確認あり |
| 規模 | 人数・アカウント・レコード・ファイル数 | 大規模母集団、複数顧客横断 |
| 完全性 | 閲覧だけでなく改変・削除・不正送信があったか | DB全削除、設定改変、不正SMS送信 |
| 回復可能性 | 組織・本人が被害状態を元へ戻せるか | パスワード変更可能、本人確認情報は回収不能 |

この八軸は点数を一つへ潰すためではなく、「何が長く残るか」を説明するために使う。

# 法制度上の重要な区分

個人情報保護委員会のガイドラインは、漏えい等の報告対象として、要配慮個人情報を含む場合、財産的被害のおそれがある場合、不正目的による行為が疑われる場合、本人1,000人超の場合などを挙げている。[^ppc-guideline]

これはDenno Watchの被害評価にも有用だが、法定報告要件と「長期的な本人被害の大きさ」は同じ概念ではない。たとえば法的報告対象であることと、二次悪用の確率・期間は分けて扱う。

# データ種別ごとの長期リスク

## 1. 認証情報

対象例:

- パスワード
- APIキー
- セッショントークン
- 秘密鍵
- 回復コード
- メールアドレスと認証情報の組み合わせ

主な被害:

- 不正ログイン。
- 資格情報の使い回しを介した他サービスへの波及。
- 管理APIやクラウドへの到達。
- 本人を装った詐欺・フィッシングの精緻化。

重要な区別:

- 平文、ハッシュ、暗号化、形式不明を分ける。
- パスワード変更済みでも、既存セッション・トークンが残る場合がある。
- メールアドレス件数とパスワード件数を合算しない。

国内例として [KDDIの共有ISPメール基盤](../incidents/2026/kddi-isp-mail-breach.md) は、メールアドレスとパスワードの影響を別件数で記録している。

## 2. 本人確認・身元証明情報

対象例:

- 運転免許証、パスポート、その他本人確認書類の画像。
- 顔写真。
- 書類番号。
- 生年月日、住所等と本人確認画像の組み合わせ。

特徴:

- パスワードのように一括変更できない。
- 画像・番号・住所など複数要素が組み合わさると、なりすましや本人確認突破へ転用される可能性がある。
- 二次悪用が発生しても、元事故と結び付けることが難しい場合がある。
- 「現時点で二次悪用を確認していない」は将来の悪用不在を意味しない。

[タイムズモビリティ / パーク２４](../incidents/2026/times-car-web-breach.md) は、一般アカウント情報と本人確認書類の影響を分けて追う必要がある代表例である。

## 3. 雇用・人事情報

対象例:

- 現職・退職者の氏名、連絡先、社員番号。
- 給与・人事評価・所属履歴。
- 退職後も保持される過去データ。

主な論点:

- 退職者は現行の社内連絡網から外れており通知が難しい。
- 長期保持により「今の従業員数」を大きく超える母集団が蓄積する。
- 組織情報と組み合わさると標的型詐欺へ利用され得る。

[第一生命グループ](../incidents/2026/daiichi-life-hr-system-breach.md) のような長期に遡る退職者情報は、**保持期間そのものが被害範囲を増幅したか**という観点で読む。

## 4. 医療・健康・要配慮情報

対象例:

- 診療・調剤情報。
- 健康診断結果。
- 障害、病歴等の要配慮個人情報。

特徴:

- 変更不能で長期にわたり本人へ結び付く。
- 差別、詐欺、社会的不利益等の可能性があり、単純な「カード番号漏えい」より回復が難しい場合がある。
- 個人情報保護委員会は要配慮個人情報を含む漏えい等を報告対象事態の一つとして示している。[^ppc-guideline]

## 5. 金融・決済・請求情報

対象例:

- カード情報。
- 口座情報。
- 請求、与信、購入情報。
- 決済履歴。

見るべき点:

- 直接決済可能な情報か、請求・購買文脈のみか。
- セキュリティコード等が含まれるか。
- 不正利用補償・再発行で被害を軽減できるか。
- 購買履歴との組み合わせで標的型詐欺に使われる可能性があるか。

[ヤマト運輸 / クロネコ代金後払い](../incidents/2026/yamato-kuroneko-postpay-breach.md) や [Ｅストアー / ショップサーブ](../incidents/2026/estore-shopserve-breach.md) は、決済そのものと購買・請求情報を分けて読む必要がある。

## 6. 位置・物流・行動情報

対象例:

- 配送先・荷送人・受取人。
- 利用日時・店舗・予約。
- 位置情報。
- 行動履歴。

単体では認証情報ほど直接的な乗っ取り能力を持たなくても、氏名・電話・住所・配送文脈と組み合わさると、信頼性の高い詐欺メッセージを作りやすくなる。

[佐川急便](../incidents/2026/sagawa-package-tracking-breach.md) では配送関連情報の「約100日分」という時間範囲自体が重要な観測値になる。

## 7. 画像・音声・自由記述

対象例:

- ユーザー画像。
- 通話音声。
- 問い合わせ本文。
- 添付ファイル。

構造化DBより内容のばらつきが大きく、「何件」という件数だけで機微性を評価しにくい。自由記述には利用者が想定外の個人情報を入力している場合もある。

[Helpfeel / Gyazo](../incidents/2026/helpfeel-gyazo-breach.md)、[ロート製薬](../incidents/2026/rohto-direct-sales-system-breach.md) などでは、構造化項目と画像・音声を別に追う価値がある。

## 8. ソースコード・設定・秘密情報

対象例:

- Gitリポジトリ。
- 設定ファイル。
- APIキー、接続先。
- CI/CD設定。

これらは個人情報ではなくても、後続侵害の足掛かりになり得る。重要なのは「リポジトリが見られた」と「本番DBが侵害された」を混同しないことである。

[株式会社イノベーション](../incidents/2026/innovation-github-breach.md) は、リポジトリ侵害と本番データ影響を分離して記録している。

## 9. 完全性・削除被害

漏えいレポートは機密性に偏りやすいが、データが**改変・削除・不正送信**された場合は別の被害軸が必要である。

[コープやまぐち](../incidents/2026/coop-yamaguchi-line-miniapp-breach.md) のDB削除、[メディア4u](../incidents/2026/media4u-sms-platform-breach.md) の不正SMSなどは、閲覧・取得だけでは説明できない。

完全性被害では次を記録する。

- 何が変更・削除されたか。
- 変更前の正しい状態を再構成できるか。
- バックアップ復旧後に欠損期間が残るか。
- 不正送信が第三者へ到達したか。
- 復旧後に監査・照合が必要か。

# 保持期間を独立した攻撃面として扱う

長期保持には、法令・契約・業務上の必要性がある場合もある。したがって「古いデータは必ず削除すべき」と単純化しない。

ただし、防御上は次の式で考えられる。

```text
潜在被害範囲
≈ 1時点の利用者規模
× 保持期間
× 複製先の数
× 一つの権限で到達できる割合
```

実際の件数をこの式で推計してはならないが、設計レビューでは有用である。

確認項目:

- 保持根拠があるか。
- 保持期限が定義されているか。
- 期限到来後に自動削除されるか。
- 本番、バックアップ、分析基盤、ログ、委託先複製を含め削除できるか。
- 過去データへ同一管理権限で到達できるか。

# 二次悪用の証拠状態

二次悪用は次の段階を分ける。

| 状態 | 意味 |
| --- | --- |
| `confirmed` | 組織・当局等が事故と関連する二次悪用を確認。 |
| `reported_unverified` | 利用者申告等はあるが事故との結び付きが未確認。 |
| `not_observed` | 調査時点で確認されていない。 |
| `unknown` | 公開情報がない。 |

「二次悪用の報告なし」を `confirmed_absent` のように扱わない。EDPBも個人データ侵害が、本人のデータ支配喪失、差別、なりすまし・詐欺、金銭的損失等につながり得ると整理している。[^edpb-breach]

# 個別レポートへ追加すると有用な項目

```yaml
data_harm_profile:
  data_classes:
    - identity_document
    - credential
    - employment
  revocability: low
  expected_value_lifetime: long
  linkability: high
  integrity_impact: none_confirmed
  retention_amplifier: possible
  secondary_abuse: not_observed
```

これは法的分類を置き換えるものではない。公開情報から読み取れる範囲を共通軸へ写像する補助メタデータである。

# 比較表で守るべきこと

1. 人数とレコード数を混ぜない。
2. 「最大影響可能性」と「確認済み取得」を同列に並べない。
3. 同じ人物が複数データ群へ重複している可能性がある場合は合算しない。
4. 変更可能な秘密と変更不能な本人属性を区別する。
5. 本人への長期リスクと企業の復旧期間を区別する。
6. 暗号化されていたという公表だけで「無害」と判断しない。鍵管理、アクセス経路、暗号化範囲が不明なら不明のままにする。

# 今後の調査課題

- 本人確認書類流出後の不正契約・金融詐欺等について、日本の公的統計と事故単位の追跡を分離して収集する。
- 事故後に提供された本人保護支援、信用監視、再本人確認等の有無を記録する。
- 退職者・休眠アカウント・古い購買履歴など、長期保持が影響人数へ寄与した事例を横断する。
- 音声・画像・自由記述のような非構造化データについて、件数以外の影響評価を標準化する。
- データ削除や不正送信など完全性被害を、漏えい件数とは別の比較表にする。

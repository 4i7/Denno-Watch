# 目的

個別インシデントのプレスリリースだけでは、経営上の意味と「事故前に何を安全対策として説明していたか」が抜ける。本台帳では各社について、次を分離して保存する。

1. **事故前資料** — 統合報告書、サステナビリティ資料、情報セキュリティ方針、リスク管理資料。
2. **事故時資料** — 初報、続報、規制報告、顧客通知。
3. **株主・投資家向け資料** — 適時開示、決算延期、業績影響、株主総会資料。
4. **事故後資料** — 調査結果、再発防止、統制KPI、行政対応。
5. **長期予後資料** — 翌期以降の統合報告、決算、再発防止進捗、追加通知。

PDFが存在する場合、本文URLだけでなくPDF又はIRライブラリ上の掲載場所を残す。資料が後日差し替えられる可能性があるため、公開日も保存する。

# 事故前資料を集める際の注意

- 後日更新されたWebページは、事故前の内容が同じだったと自動的にみなさない。
- 統合報告書の発行日が事故後なら「事故前統制」の根拠にしない。
- 事故年度の統合報告書でも、原稿締切が事故前か事故後かを可能な限り確認する。
- KPIの「目標」と「実績」を分ける。
- ISMS認証範囲が公表されていない場合、グループ全体へ拡張しない。
- 企業がセキュリティ製品・サービスを販売していることを、自社環境への同一統制の導入証拠にしない。

# 目的

個人情報漏えいは「何件」「何人」で比較しやすい。一方、完全性侵害は数字にしにくいため、重大でも比較表から落ちやすい。

しかし、次のような事故は「データが外へ出たか」だけでは評価できない。

- データベースが削除された。
- 正規アカウントから偽のSMS・メールが送信された。
- 受注・請求・在庫・設定が改変された。
- バックアップが削除された。
- 権限・ルール・送金先が変更された。
- Webや配布物が改ざんされた。
- ログが消去・変更された。

Denno Watchでは、**機密性、完全性、可用性、信頼経路の悪用**を分けて記録する。

# 完全性被害を七種類へ分ける

| 類型 | 内容 | 主な危険 |
| --- | --- | --- |
| データ破壊 | DB・ファイル・記録の削除 | 業務停止、履歴喪失 |
| データ改変 | 値・記録・取引の変更 | 誤判断、不正決済、品質問題 |
| 制御設定改変 | 権限、ルール、設定、ルーティングの変更 | 継続的な不正操作 |
| 正規機能の悪用 | 正規SMS・メール・APIから不正操作 | 高い信頼性を持つ詐欺・下流被害 |
| ログ・証拠破壊 | 監査ログ削除、時刻・履歴改変 | 原因・範囲確定不能 |
| 復旧基盤破壊 | バックアップ、スナップショット、復旧設定の削除 | 長期停止、身代金圧力 |
| ソフトウェア／供給物改変 | コード、ビルド、更新物、設定配布の改変 | 多数組織への波及 |

# 機密性と完全性は同時にも独立にも起きる

たとえば攻撃者がDBへ到達した場合、次は別々の事実である。

```text
閲覧した
取得した
外部転送した
変更した
削除した
```

「全削除された」ことから「全件持ち出された」とは言えない。逆に、削除前に取得されていても外部転送ログが残らない場合がある。

したがって、完全性被害を漏えいの証拠として代用しない。

# 国内例1: コープやまぐち — DB全削除

コープやまぐちの2026年8月事例では、第三者がLINEミニアプリ用DBへ不正アクセスし、**DB内の全データを削除**した。外部アクセス遮断後、同日中にバックアップから復元してサービスを再開している。[^coop-yamaguchi]

この事例の重要点は次の通り。

- 完全性への実害は確認済み。
- 可用性への影響も確認済み。
- バックアップにより同日復旧。
- 外部持ち出しは別の調査事項であり、削除事実から流出を確定しない。

「漏えい件数」の列だけを見ると、この事故の主要な技術被害を取り逃す。

# 国内例2: メディア4u — 正規SMS送信権限の悪用

メディア4uの2026年事例では、管理情報95,412レコードの流出に加え、一つの顧客アカウントを通じ**280件の不正SMS送信**が確認された。[^media4u]

これは単なるデータ漏えいではない。攻撃者が正規通信基盤の送信能力を利用したため、受信者から見ると通常の送信経路に見える可能性がある。

この類型では次を別に追う。

- 何件送信・操作されたか。
- どの正規ID・テナント・権限が使われたか。
- 他顧客へ横展開したか。
- 送信先へ訂正・注意喚起できたか。
- 認証情報・トークンを全無効化できたか。

# 「正しい状態」をどう証明するか

完全性事故では、単にサービスを再開するだけでなく、**現在の状態が正しいこと**を確認する必要がある。

## データ

- 期待件数と一致するか。
- ハッシュ・署名・チェックサムが使えるか。
- 外部システムの記録と照合できるか。
- 変更履歴が残っているか。

## 取引

- 二重処理がないか。
- 欠落注文・欠落決済がないか。
- 不正な送金先・配送先変更がないか。
- 事故期間の手作業を再投入したか。

## 構成

- IAMポリシー。
- ファイアウォール・ルーティング。
- メール・SMS送信設定。
- API連携。
- CI/CD。
- バックアップ保持設定。

## コード・配布物

- 信頼できるコミット・署名・ビルド成果物と一致するか。
- 依存パッケージ・更新サーバーが改変されていないか。

# 完全性監視で有効な証拠

- 変更監査ログ。
- DBトランザクションログ。
- バージョン管理。
- オブジェクトバージョニング。
- 署名。
- ハッシュ。
- イミュータブルログ。
- 外部独立系の取引記録。
- 時刻同期された監査証跡。

重要なのは「改変を防ぐ」だけでなく、「何が変わったか再構成できる」こと。

# バックアップ破壊

CISAのStopRansomware Guideは、ランサムウェア攻撃者がアクセス可能なバックアップを探索し削除・暗号化することを前提に、オフライン・暗号化バックアップと定期試験を推奨している。[^cisa-stopransomware]

バックアップ破壊は、通常データの完全性侵害より重い場合がある。現在の状態だけでなく、**正しい過去状態へ戻る能力**まで失うためである。

詳細は [バックアップ・復元可能性・クリーン復旧](backup-recoverability-and-clean-restoration-knowledge-base-2026-10-04.md) を参照する。

# 業務完全性

技術的なデータが正しくても、事故中の手作業・代替運用で業務整合性が崩れる場合がある。

例:

- 紙受注を後からシステムへ再入力して重複注文。
- 一時的な代替決済から本番決済へ二重請求。
- 在庫情報の同期ずれ。
- 予約の重複・欠落。
- 通知漏れ。

したがって、復旧完了条件には業務側の照合も含める。

# 信頼経路の悪用

SMS、メール、公式Web、プッシュ通知、顧客ポータルなどは、組織から利用者へ信頼情報を送る経路である。

攻撃者がこの経路を使うと、情報漏えいがなくても被害が生じる。

Denno Watchでは次を記録する。

```yaml
trusted_channel_abuse:
  channel: sms
  confirmed_actions: 280
  affected_tenants: 1
  credentials_rotated: confirmed
  recipient_notification: unknown
```

# 破壊的操作の時間軸

可能であれば次を分離する。

```text
侵入
↓
不正権限取得
↓
閲覧・偵察
↓
改変 / 削除 / 不正送信
↓
検知
↓
不正操作停止
↓
復元
↓
整合性照合
↓
通常業務
```

検知時刻と破壊開始時刻が同じとは限らない。

# メタデータ候補

```yaml
integrity_impact:
  status: confirmed
  destructive_actions: []
  unauthorized_modifications: []
  trusted_channel_abuse: []
  evidence_destruction: unknown
  recovery_assets_targeted: unknown
  last_known_good_state: null
  restoration_completed_at: null
  reconciliation_completed_at: null
```

完全性影響が公表されていない事故へ、ランサムウェアという理由だけで `confirmed` を付けない。

# 経営指標

- 重要データで変更履歴を追える割合。
- 重要設定の無承認変更を検知する時間。
- 正規通信経路を緊急停止できる時間。
- 破壊後に最後の正常状態を特定できる時間。
- バックアップからの復元後、業務照合を終える時間。
- 重要取引で二者承認・署名・外部照合がある割合。

# 今後の比較対象

国内42件を再監査する際、次を検索する。

- 「削除」「消去」「改ざん」「変更」「不正送信」「不正登録」「不正決済」。
- バックアップ削除・暗号化。
- ログ削除。
- 管理者・権限設定変更。
- 正規メール・SMS・APIの悪用。
- サービス復旧後のデータ照合。

これにより、漏えい件数中心の比較から、**組織が正しい状態を維持・回復できたか**へ分析を広げられる。

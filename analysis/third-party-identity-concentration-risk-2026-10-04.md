# 要旨

現代の大規模インシデントでは、被害規模を決めるのは被害企業のサーバー台数だけではない。**誰の認証で入れるか、誰のデータを預かっているか、何社が同じ基盤へ依存しているか、復旧を誰に依存しているか**という集中構造が、一つの侵害を多数の組織へ増幅する。

金融庁も2026年に、金融機関のサードパーティ・サイバーセキュリティリスク管理を独立した調査対象として、米国・EU・英国の大手金融機関の管理手法を調査している。Denno Watchでは、第三者リスクを単なる「委託先評価票」ではなく、技術・認証・データ・復旧の依存関係として記録する。

# 集中リスクを4種類に分ける

## 1. 認証集中

一つの資格情報、セッション、管理アカウント、委託先端末が、複数システム・複数顧客へ到達できる状態。

代表的な増幅条件:

- MFA未適用またはフィッシング耐性のない認証。
- 長寿命のパスワード、APIキー、PAT、サービスアカウント。
- 委託先が複数顧客へ同じ端末から接続。
- 退職・契約終了後も残る認証情報。
- 接続元制限や端末信頼がない。
- 本番、管理、バックアップが同じ認証基盤へ依存。

Snowflakeを狙ったUNC5537では、Mandiantが対応した事例はSnowflake企業環境の侵害ではなく、盗まれた**顧客側認証情報**へ遡った。MandiantとSnowflakeは約165組織へ潜在的な露出を通知し、攻撃者が利用したアカウントの少なくとも79.7%で過去の認証情報露出が確認された。最古の関連情報窃取型マルウェア感染は2020年11月まで遡り、資格情報が数年間有効なままだった例もある。

さらにMandiantは、個人用途にも使われた委託先端末が情報窃取型マルウェアへ感染し、一台から複数顧客へのアクセスが危険にさらされ得る事例を確認している。これは「委託先企業が安全か」ではなく、**委託先のどの端末・どの認証情報が何社へ到達できるか**まで把握する必要性を示す。

## 2. データ集中

一つのSaaS、分析基盤、BPO、ファイル転送製品、共通DBに、多数の企業・顧客・期間のデータが集まる状態。

増幅条件:

- テナント間の論理分離が弱い。
- 分析・移行・バックアップ用コピーが長期間残る。
- 顧客ごとの暗号鍵、権限、監査ログが分離されていない。
- 退会者・退職者・過去応募者等の不要データを保持。
- 取得量・エクスポート量に境界がない。

国内ではApplyNow、両毛システムズ、日本テレネット、KDDI等が、主被害組織だけでなく委託元・利用組織・顧客データへ波及する構造を示す。

## 3. 供給・サービス集中

ある製品、提供事業者、決済・通信・医療・物流基盤が、多数の下流組織の業務へ必須となる状態。

Change Healthcareでは、サイバー攻撃により米国医療の請求・決済等へ広範な影響が生じ、UnitedHealth Groupは2024年末までに医療提供者へ90億ドル超の無利子融資を提供した。2024年の直接対応費は22億ドル、Optum Insightの事業中断影響は8.67億ドルと開示された。ここで重要なのは単一企業のIT損害ではなく、**下流の医療提供者が資金繰りまで影響を受けたこと**である。

## 4. 復旧集中

事故時に復旧の鍵を同じ第三者、同じクラウド、同じ認証基盤、同じバックアップ管理面へ依存している状態。

- 本番とバックアップの管理者が同じ。
- DR環境が同じID基盤・同じリージョン・同じ提供事業者へ依存。
- 復旧に必要なソフトウェア、鍵、手順書、担当者が一か所に集中。
- 委託先が停止すると自社だけでは復旧できない。

第三者リスク管理では「侵害されないこと」だけでなく、**侵害された第三者なしでも最低限の業務を再開できるか**を評価する。

# 共有責任を「責任逃れ」にしない

SaaS・クラウドでは、提供事業者と顧客の責任境界がある。しかし事故分析では、次の三つを同時に記録する必要がある。

1. **どの環境が侵害されたか** — 提供事業者本体、顧客テナント、委託先端末等。
2. **どの統制を誰が実装する責任だったか** — MFA、ネットワーク制約、鍵管理、ログ等。
3. **実際に被害を抑える設計として十分だったか** — デフォルト、強制設定、危険設定の可視化、異常検知、支援体制等。

Snowflakeの2024年事例ではMandiantはSnowflake企業環境の侵害を確認していない。一方、Snowflake自身の2026年開示では、この顧客アカウント侵害を巡る多数の訴訟、規制調査、議会関係者からの照会、評判への影響が継続している。**法的責任の最終判断と、集中サービスを安全に設計する経営責任は別問題**である。

# 委託先・SaaSを評価するための証拠チェックリスト

## 認証

- MFAは管理者だけでなく全外部アクセスへ強制されるか。
- フィッシング耐性のあるFIDO2等を選べるか、または必須化できるか。
- 顧客側でMFA未設定アカウントを一覧化・禁止できるか。
- 契約終了・長期未使用アカウントを自動失効できるか。
- APIキー・トークンの有効期限とローテーションがあるか。
- 接続元IP、ASN、端末信頼、国・地域等で制限できるか。

## 接続

- 委託先がどのネットワーク・アプリ・管理面へ到達できるか。
- 顧客ごとに接続権限が分離されているか。
- 一つの委託先端末から複数顧客へ管理権限で接続しない設計か。
- 緊急時に委託先接続だけを即時停止できるか。

## データ

- 預託するデータ種別、件数、保持期間、保存場所。
- 本番、分析、バックアップ、移行用コピーの所在。
- 顧客・テナント単位の論理分離、鍵分離、アクセスログ。
- 契約終了時の削除証跡。
- 再委託先へどのデータが渡るか。

## 監視

- 誰が認証ログ、管理操作、大量取得、エクスポートを監視するか。
- 顧客が自らSIEMへログを取り込めるか。
- 異常な大量アクセスを自動停止できるか。
- ログ保持期間がフォレンジックに十分か。

## 復旧

- RTO/RPOは契約上の数字だけでなく演習で測定しているか。
- 顧客データを個別に復元できるか。
- 本番とバックアップで認証・管理面が分離されているか。
- 提供事業者が長期停止した場合の代替手段があるか。
- 復旧時に顧客側で再認証・鍵交換・接続確認できるか。

# 契約に必要な最低限の論点

契約書だけでは防御にならないが、事故時の不確実性を減らすために次を明文化する。

- インシデント通知の起点と期限。
- 初報で最低限共有する事実。
- 顧客がログ・証拠・フォレンジック結果へアクセスできる条件。
- 再委託先の通知と管理責任。
- 認証情報・鍵の緊急失効手順。
- データ返却・削除・削除証跡。
- 業務継続・復旧支援と優先順位。
- 規制当局・本人通知を誰が実施するか。
- 損害、補償、保険、求償の責任境界。
- 契約終了後も続く調査・通知・訴訟への協力義務。

# 集中リスクを数字で見る

製品数やベンダー数だけではなく、次の指標を持つ。

| 指標 | 意味 |
| --- | --- |
| 単一認証情報到達範囲 | 一つの認証情報で到達可能な重要システム・顧客数 |
| 単一委託先到達範囲 | 一社の委託先が持つ本番・管理権限の範囲 |
| 単一SaaSデータ集中度 | 一つのサービスに存在する顧客・本人・機微データ量 |
| 最大下流組織数 | 一つの事故で同時通知が必要になり得る顧客・委託元数 |
| 復旧単一依存数 | 一つのID基盤、クラウド、バックアップ、担当者に依存する重要業務数 |
| 代替不能時間 | 当該第三者なしで重要業務を維持できない時間 |
| ログ独立性 | 提供事業者停止時にも自社で保持・解析できる証拠の割合 |

# 国内事例への読み替え

- **ApplyNow**: 採用SaaSへ応募者・雇用関連データが集中し、利用企業へ下流影響が生じる。
- **両毛システムズ／日本テレネット**: 受託・BPO構造により、自社侵害が顧客組織のデータ問題になる。
- **KDDI**: 共有ISPメール基盤の侵害は、多数利用者の認証情報と下流サービスへ波及し得る。
- **メディア4u**: 顧客データだけでなく、正規SMS送信権限という信頼チャネル自体が集中資産になる。
- **LEAN BODY／VOISING**: BI・分析基盤が「補助システム」ではなく本番データ境界になる。
- **イノベーション**: GitHub認証情報とリポジトリ内データ配置が重なると、開発基盤が顧客情報の流出経路になる。
- **タイムズカー**: 本人確認書類の集中保有は、件数だけでなく長期的な身元悪用可能性を増幅する。

# 経営上の判断

第三者リスクの本質は「その会社を信用できるか」ではない。**その会社・製品・認証情報が破られたとき、自社と何社の顧客が、どの速度で、どこまで巻き込まれるか**である。

最低限、重要第三者ごとに次の4点を答えられる状態にする。

1. 何の認証・接続を許しているか。
2. 何のデータを、どこに、いつまで置いているか。
3. 一社の障害でどの業務・顧客へ波及するか。
4. その第三者を使えなくても復旧・継続できるか。

この4点が不明な重要委託先は、契約上のセキュリティ評価が高得点でも集中リスクは未管理である。

# 現時点で残る主要ギャップ

今回、当初P0/P1だった財務、開示品質、バックアップ、完全性、依存グラフまで独立資料化した。残る不足は、**一時点の公開資料だけでは答えが出ず、今後の継続観測が必要な領域**が中心となった。

## P0: 再発防止策の実効性・再発追跡

事故後の「MFA強化」「監視強化」「教育徹底」「再構築」は、発表時点では効果を証明しない。

今後追うもの:

- `planned`、`in_progress`、`implemented`、`independently_verified` を分ける。
- 同一組織で数年後に同型事故が再発したか。
- 同じ委託先・共有基盤から別顧客へ再波及したか。
- 分離、代替経路、権限削減等が実際に依存グラフを変えたか。
- サービス廃止・置換が恒久的なリスク低減になったか。

2026年単年では判断できないため、2027年以降の主要継続課題とする。

## P1: サイバー保険・損害移転の国内実測

財務資料で保険を扱う枠組みは追加したが、日本企業の事故単位で公開される保険金、免責、上限、求償、更新条件はまだ少ない。

今後追うもの:

- 実際の保険回収額。
- 総費用と保険控除後純額。
- 保険枠の消尽。
- 訴訟・通知・休業損失等の補償範囲。
- 事故後の引受条件・保険料変化。

## P1: 人員・組織疲弊

公開レポートで最も観測しにくい領域の一つ。

調査候補:

- 24時間対応の期間。
- 通常開発・運用の停止。
- 外部専門家への長期依存。
- 採用、離職、異動。
- 経営陣・取締役会の継続関与。
- 復旧後の技術負債。

断片情報を人数や人時へ無理に推計しない。

## P1: 本人の二次被害・詐欺追跡

「二次悪用を確認していない」で追跡を終えず、長期的に次を調べる。

- なりすまし契約。
- フィッシング・詐欺。
- 不正口座・決済。
- 本人確認の再実施。
- 信用監視等の支援。

公的統計と特定事故の因果を混同しない証拠設計が必要。

## P1: クラウド・SaaS共有責任と証拠境界

第三者・集中リスクと依存グラフで構造は扱えるが、責任分界と証拠取得能力は独立資料化の価値が残る。

追加候補:

- SaaS管理者と顧客管理者の責任境界。
- 顧客側で有効化すべきMFA・ログ・アクセス制御。
- 提供者側でしか取得できない証拠。
- 契約終了時の削除・エクスポート。
- 管理API、OAuth、連携アプリの横断権限。
- 障害時に顧客が独立して最低限の調査・復旧を行えるか。

Snowflake比較ケースと国内SaaS事例を接続して深掘りする価値が高い。

## P2: ソフトウェア・OSSサプライチェーン

ベンダー／委託先のサプライチェーンとは別に、開発・配布経路を扱う。

対象:

- パッケージ依存関係。
- CI/CD。
- パッケージレジストリ。
- 署名・アーティファクト。
- ビルド環境。
- リポジトリ秘密情報。

## P2: AIシステム自身のセキュリティ

既存AIレポートは主に攻撃者側の経済性を扱う。企業内AIを守る領域として、次を別途整理できる。

- エージェントのツール権限。
- プロンプトインジェクション。
- 機密情報の外部送信。
- RAG・モデル・データへのアクセス制御。
- APIキー、サービスアカウント。
- AI生成コードの供給網。
- 自動操作の承認境界と監査ログ。

## P2: 暗号・長期機密性

数十年保持する高感度データでは鍵管理、暗号更新、将来の暗号移行も長期課題となる。ただし現在の42件から直接導ける公開根拠は限定的なので中心テーマへ無理に入れない。

## P2: 物理アクセス・IoT・モバイル

現在の事例集はサーバー、Web、SaaS、業務基盤が中心。IoT、デジタルキー、物理アクセス制御、モバイル固有の重大事例が増えた場合に独立分析へ昇格する。

# 新しい資料同士の接続

```text
個別インシデント
    │
    ├─ 何が起きたか → ライフサイクル
    ├─ なぜ広がったか → 第三者・認証・集中リスク / 依存グラフ
    ├─ 何が壊れたか → データ被害 / 完全性 / OT安全
    ├─ 何を直すか → 失敗モードと防御統制
    ├─ 何から戻すか → バックアップ・クリーン復旧
    ├─ 誰へ報告するか → 報告・通知・公表マップ
    ├─ 公表は十分か → 公表品質・透明性
    ├─ いつ復旧とするか → 復旧判定・対応指標
    ├─ いくら残るか → 財務・事業影響 / 長期予後
    └─ いつ再確認するか → 情報源の鮮度・再確認基準
```

# ナレッジベースの品質指標

件数だけをKPIにしない。

## 網羅性

- 重大事例の収録数。
- 業種・被害型・侵入型の偏り。
- `unknown` が多いフィールドの種類。

## 証拠品質

- 一次情報を少なくとも一つ持つ事例率。
- 主張と脚注が対応している割合。
- 二次情報しかない主張の件数。

## 鮮度

- 活動中・収束中事例で `public_record_checked_at` が古い件数。
- 新公表からKB更新までの時間。

## 時系列品質

- 検知、公表、封じ込め、復旧、通知を分離できている割合。
- 訂正前値を保持している割合。

## 復旧品質

- バックアップの存在だけでなく、復元・分離・照合を確認できる事例数。
- 技術復旧と業務復旧を分けられる事例率。

## 長期追跡

- 技術復旧後に再確認された事例率。
- 決算、規制、二次悪用、保険、再発まで追跡した事例数。

## 再利用性

- 共通失敗モードへ分類できる事例率。
- 防御統制の「確認済み」と「推奨」を分離できる割合。
- 依存関係を公開根拠付きで表現できる事例数。

# 最終的な到達像

Denno Watchの価値は事件一覧を増やすことではなく、ある事故について次の問いを同じ証拠基盤から辿れることにある。

- いつ何が起きたか。
- 何が確定し、何がまだ不明か。
- 何人・何件ではなく、どの種類の被害が残るか。
- 何が削除・改変・悪用されたか。
- どこで被害が増幅し、どの分離が被害を抑えたか。
- 何を止めれば類似事故の確率又は被害範囲を下げられるか。
- バックアップから本当に安全に戻せるか。
- 復旧したと言える条件は何か。
- 誰へ何を報告・通知・開示する必要があるか。
- 公表された情報は利用者・取引先・投資家が行動できる品質か。
- 技術復旧後に財務・本人・規制・訴訟・人員の何が残るか。
- その事実はいつ、どの情報源で再確認されたか。
- 数年後、再発防止策が実際に効いたか。

今回の拡張で、事故の時間軸に加え、**制度、データ被害の質、完全性、財務、防御統制、バックアップ、OT安全、公表品質、依存関係、情報源の鮮度**が独立軸として接続された。今後の最大の課題は、2027年以降まで時間を必要とする**再発防止策の実効性と長期的な再発追跡**である。

# 目的

Denno Watchは、2026年の国内重大インシデント42件、海外比較ケース、事故のライフサイクル、復旧、第三者・認証・集中リスク、長期予後、対応指標、防衛予算、業種別最大被害、AI時代の攻撃経済性までを既に持つ。

本監査では、既存資料を「十分か／不足か」という二値ではなく、次の観点で再点検した。

1. 個別事故を読むために不足する観測項目はないか。
2. 複数事故を比較すると初めて見える領域はないか。
3. 技術復旧後の長期影響を追う資料が足りているか。
4. 制度・経営・財務・人・サプライチェーン・物理安全まで接続できるか。
5. 情報源の更新を継続的に検知できるか。
6. 一つの結論を複数の独立資料から検証できるか。
7. 現在の国内事例だけでは観測できない尾部を、海外比較で補えるか。
8. 「分からないこと」を構造化して次の調査へ送れるか。

# 現在の知識基盤を六層に分ける

Denno Watchは、今後次の六層として考えると拡張しやすい。

```text
A. 事実層
   個別インシデント、一次情報、時系列、影響、復旧

B. 比較層
   国内横断、海外比較、業種比較、失敗モード比較

C. 被害層
   可用性、機密性、完全性、本人被害、財務、社会、安全

D. 防御層
   統制、検知、対応、復旧、事業継続、再発防止

E. 制度・経営層
   法規制、通知、市場開示、予算、ガバナンス、保険

F. 継続保守層
   情報源、鮮度、再確認、訂正、長期予後、再発追跡
```

従来はA、B、Dが特に強く、Cの一部、E、Fに独立資料としての不足が残っていた。今回の拡張でその差を縮めた。

# 既存資料へ追加すべき横断項目

新しい独立資料だけでは不十分である。個別事例の公開根拠が十分な場合、次を段階的に取り込む価値がある。

| 項目 | 理由 | 追加先 |
| --- | --- | --- |
| 報告・通知の時刻 | 技術初動と制度対応の差を比較できる | 個別事例メタデータ |
| 市場開示・決算影響 | 技術復旧後の財務尾部を追える | 上場会社事例 |
| データ被害プロファイル | 人数だけでない長期リスクを比較 | 高感度データ事例 |
| 確認済み統制・事故後統制 | 再発防止策を事実として追える | 公表がある事例 |
| OT安全・操業状態 | 物理系事故で「復旧」の意味を精密化 | OT・重要インフラ事例 |
| 情報源状態 | 廃止・置換・更新を追える | 方法論・出典管理 |
| 再確認優先度 | 古い42件を均等監視せず重要度で保守 | 研究キュー |

すべての過去事例へ一度に空欄フィールドを追加する必要はない。実質更新時に、公開根拠がある項目から後方互換的に追加する方がよい。

# まだ独立資料化する価値が高い領域

以下は今回の拡張後も残る。重要度、公開根拠の量、既存資料との重複を考慮して優先順位を付ける。

## P0: 財務・事業影響の実測

### なぜ不足しているか

防衛予算モデルでは想定損失を扱っているが、実際の事故で公表された費用を統一的に追う台帳はまだない。

### 独立資料候補

`incident-financial-and-business-impact-ledger.md`

### 分けるべき費用

- 売上・受注・出荷停止による逸失。
- フォレンジック・外部専門家。
- システム再構築。
- 顧客補償。
- 本人通知・コールセンター。
- 法務・訴訟。
- 行政対応。
- 保険金。
- 再発防止投資。
- 廃棄・品質保証・再処理。
- 長期的な事業撤退・サービス終了。

「推計損失」と「会社が開示した実績」を絶対に同じ列へ入れない。

## P0: 開示品質・透明性の比較

### 価値

インシデントそのものだけでなく、組織がどの速度・精度で情報を更新したかは、顧客保護と下流対応へ直結する。

### 評価候補

- 初報までの時間。ただし検知時刻が公開されている場合だけ。
- 初報で明示した不明点。
- 件数訂正の透明性。
- 誤った初期認識を後から訂正したか。
- 復旧と調査完了を混同していないか。
- 本人・顧客が取るべき行動を具体的に示したか。
- 過去の公表を消さず履歴を残しているか。

これは企業の「点数付け」より、公開情報の再利用性を測る形が適切である。

## P0: 再発防止策の実効性・再発追跡

事故後に「MFA強化」「監視強化」「教育徹底」と公表されても、効果はその時点では分からない。

必要な長期追跡:

- 同一組織で数年後に同型事故が再発したか。
- 同じ委託先・共有基盤から別顧客へ再波及したか。
- 公表した統制が後続資料で実装済みになったか。
- サービス・システム廃止が恒久対策となったか。

2026年単年の事例集では答えが出ないため、2027年以降の継続観測が必要である。

## P1: サイバー保険・損害移転

見るべき項目:

- 保険金の公表額。
- 免責・上限。
- 復旧費、休業損失、訴訟、通知等のどこが対象か。
- 保険者との争い・求償。
- 事故後の更新条件・保険料。
- セキュリティ統制が引受条件へどう接続されたか。

国内一次情報が少ない場合は、海外比較ケースで長期尾部を補う。

## P1: 人員・組織疲弊

技術復旧には人間の継続稼働が必要だが、公開レポートでは見落とされやすい。

調査項目:

- 24時間対応の期間。
- 開発・運用の通常業務停止。
- 外部専門家への長期依存。
- 採用・離職・異動。
- 経営陣・取締役会の関与。
- 復旧後の技術負債。

公開定量情報が少ないため、断片的な事例を無理に統計化しない。

## P1: 本人の二次被害・詐欺追跡

個人情報漏えい後の被害は「二次悪用を確認していない」で追跡が止まりやすい。

必要な調査:

- なりすまし契約。
- フィッシング・詐欺。
- 不正口座・決済。
- 本人確認の再実施。
- 信用監視等の支援。
- 公的統計と特定事故の因果を混同しない証拠設計。

## P1: サービス依存・集中リスクのグラフ化

現在の第三者・認証・集中リスクは文章分析として強い。次段階では、依存関係をグラフとして管理すると波及を比較しやすい。

ノード候補:

- 被害組織。
- サービス提供者。
- IDプロバイダー。
- MSP/MSSP。
- クラウド。
- SaaS。
- BPO。
- 決済・物流・通信。
- 重要な下流顧客。

エッジ候補:

- 認証依存。
- 管理権限。
- データ保管。
- バックアップ。
- 通信。
- 業務継続。
- 通知義務。

一つのベンダー名を「リスク」とするのではなく、どの依存が単一点故障なのかを表す。

## P1: クラウド・SaaS共有責任

追加価値が高い観点:

- SaaS管理者と顧客管理者の責任境界。
- テナント分離。
- 顧客側で有効化すべきMFA・ログ・アクセス制御。
- ベンダー側でしか取得できない証拠。
- 契約終了時のデータ削除・エクスポート。
- 管理API・連携アプリ・OAuth等の横断権限。

Snowflake比較ケースと国内SaaS事故を接続しやすい。

## P1: バックアップ・復元可能性の実証台帳

「バックアップあり」ではなく、次を比較する。

- 分離されていたか。
- 攻撃者から削除可能だったか。
- 復元試験済みか。
- 構成・秘密情報も復元できるか。
- どの時点へ戻ったか。
- データ損失期間。
- 本番再開までの実測時間。
- 復旧後の整合性確認。

コープやまぐちのような迅速復旧と、クリーン再構築が必要なランサムウェア事例を比較できる。

## P1: 完全性被害の独立台帳

個人情報流出は件数化しやすい一方、削除、改変、不正送信、偽情報、設定変更は別軸である。

対象例:

- DB削除。
- 不正SMS。
- コンテンツ改ざん。
- 取引・請求情報の改変。
- ソース・CI設定の改変。
- バックアップ削除。

機密性中心の漏えい統計に埋没させない。

## P2: ソフトウェア・OSSサプライチェーン

今後の対象:

- 開発依存関係。
- CI/CD。
- パッケージレジストリ。
- 署名・アーティファクト。
- ビルド環境。
- リポジトリ秘密情報。

ベンダー／委託先のサプライチェーンと、ソフトウェア供給網を別にする。

## P2: AIシステム自身のセキュリティ

既存のAIレポートは攻撃者側の自動化・経済性を主に扱う。別軸として、企業がAIを導入したことで増える守る対象も整理できる。

例:

- エージェントのツール権限。
- プロンプトインジェクション。
- 機密情報の外部送信。
- モデル・RAGデータへのアクセス制御。
- APIキー・サービスアカウント。
- AI生成コードの供給網。
- 自動操作の承認境界と監査ログ。

「AIが危険」という総論ではなく、既存のID・データ・権限・サプライチェーンへどう接続するかを中心にする。

## P2: 暗号・長期機密性

高感度データの保持期間が数十年に及ぶ場合、暗号鍵管理・暗号更新・将来の暗号移行も長期的な問題になる。ただし現在の2026事故事例から直接導ける範囲は限定的なので、事故レポートの中心へ無理に入れない。

## P2: 物理アクセス・IoT・モバイル

現在の事例集はサーバー、Web、SaaS、業務基盤が中心である。今後、IoT、モバイルアプリ、デジタルキー、物理アクセス制御等の重大事例が増えた場合に独立分析へ昇格する。

# 海外比較ケースを追加するなら何を補うべきか

海外事例は有名さではなく、国内42件で観測できない現象を補うために選ぶ。

| 不足現象 | 比較ケースの選定条件 |
| --- | --- |
| OT・安全 | 物理プロセス停止、安全確認、手動運転まで公表された事例 |
| 長期財務 | 数四半期にわたる費用・保険・訴訟が追える事例 |
| 本人二次被害 | 信用監視、詐欺、補償等まで長期観測できる事例 |
| クラウド共有責任 | 顧客側資格情報とサービス側責任境界が明確な事例 |
| ソフトウェア供給網 | 開発・配布経路から多数組織へ波及した事例 |
| 重要インフラ | 他分野へ供給影響が連鎖した事例 |
| 開示義務 | 市場開示と規制報告の時系列を比較できる事例 |

海外事例の件数を増やすこと自体は目的にしない。

# 新しい資料同士の接続

```text
個別インシデント
    │
    ├─ 何が起きたか → ライフサイクル
    ├─ なぜ広がったか → 第三者・認証・集中リスク
    ├─ 何が壊れたか → データ被害・OT安全
    ├─ 何を直すか → 失敗モードと防御統制
    ├─ 誰へ報告するか → 報告・通知・公表マップ
    ├─ いつ復旧とするか → 復旧判定・対応指標
    ├─ 何年残るか → 長期予後
    ├─ いくら備えるか → 防衛予算
    └─ いつ再確認するか → 情報源の鮮度・再確認基準
```

この形にすると、個別事故から「原因」「被害」「対策」「制度」「予後」「再確認」へ往復できる。

# ナレッジベースの品質を測る指標

件数だけをKPIにしない。次の方が品質を反映しやすい。

## 網羅性

- 重大事例の収録数。
- 業種・被害型・侵入型の偏り。
- `unknown` が多いフィールドの種類。

## 証拠品質

- 一次情報を少なくとも一つ持つ事例率。
- 主張と脚注が対応している割合。
- 二次情報しかない主張の件数。

## 鮮度

- P0/P1事例で `public_record_checked_at` が古い件数。
- 新公表からKB更新までの時間。

## 時系列品質

- 検知、公表、封じ込め、復旧、通知が分離されている割合。
- 訂正前値が保持されている割合。

## 長期追跡

- 技術復旧後に再確認された事例率。
- 決算・規制・二次悪用まで追跡した事例数。

## 再利用性

- 共通失敗モードへ分類できる事例率。
- 防御統制の「確認済み」と「推奨」を分離できている割合。

# 最終的な到達像

Denno Watchの価値は「事件一覧を増やすこと」ではなく、ある事故について次の問いを同じ証拠基盤から辿れることにある。

- いつ何が起きたか。
- 何が確定し、何がまだ不明か。
- 何人・何件ではなく、どの種類の被害が残るか。
- どこで被害が増幅したか。
- 何を止めれば類似事故の確率又は被害範囲を下げられるか。
- 復旧したと言える条件は何か。
- 誰へ何を報告・通知する必要があるか。
- 技術復旧後に財務・本人・規制・訴訟・人員の何が残るか。
- その事実はいつ、どの情報源で再確認されたか。
- 数年後、再発防止策が実際に効いたか。

今回の拡張で、事故発生から長期予後までの時間軸に加え、**制度、データ被害の質、防御統制、OT安全、情報源の鮮度**が独立した軸として接続された。次の大きな空白は、実測財務影響、開示品質、再発防止策の実効性、バックアップ実証、完全性被害、依存グラフである。
